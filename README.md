# Shisa(シーサー) — お店の守り神

**インストールするだけで、お店を守ってくれる守り神。**

レンタルサーバーで動く EC-CUBE のお店のための、自分で考えて守りを固める Agent です(コード名 self-harden)。サーバー会社からセキュリティのお知らせが届いても、小さなお店の店主さんは、読んでも何のことかわかりません。開発会社に頼めば数日から数週間かかります。そのあいだも、攻撃は待ってくれません。

Shisa は、お店に入れたその時から、自分でお店を見張ります。届いたお知らせの URL を貼れば、そのお知らせがこのお店に当てはまるかを自分で調べ、このサーバーで本当に効く手を試してから、お店を止めずに守りを入れます。

Built with Claude: Japan 2026 の応募作品です。

## 何をするか

1. 調べる: PHP の版と動かし方、設定、EC-CUBE の版、中の部品、外から見えてはいけないファイルを、自分で調べます。公開された弱点の情報も、公式の一次資料で確かめます。
2. 照らし合わせる: お店のファイルを、EC-CUBE 公式の配布物と 1 つずつ見比べます。書き換えられたファイルは公式の中身に戻し、覚えのないファイルは消さずに隔離します。
3. 試す: 設定の変更は、いきなり本番に入れません。お店に影響のない試験場を作って、そこで効くかどうか、お店が止まらないかを先に確かめます。同じ設定でも、サーバーの作りによって効いたり、お店が止まったりするからです。
4. 入れて確かめる: 本番に入れたら、すぐにお店を開いて確かめます。開けなくなっていたら、その場で元に戻します。
5. 上げる: EC-CUBE や中の部品に、同じ系列の公式の修正版があれば、ファイルを全部そろえて当てます。composer を動かさずに、公式の配布物どおりに置きます。修正版がない弱点は、外から届くかを確かめ、届くなら入口で塞ぎます。
6. 報告する: 直したこと、次の点検で Shisa がやること、店主さんの判断を待つこと(メンテナンスが要る作業)、サーバー会社にお願いすること(依頼文つき)を、店主さんにわかる言葉で書きます。管理画面には「お店の健康診断」の表で出します。

特定の弱点や回避策の答えは、Agent への指示とコードのどちらにも書いていません。毎回、自分で調べて導きます。

## 形

```
  店主さん ── 管理画面(プラグイン)── 「通知を渡す」
                                        │
                                        ▼
  API(頭:Claude) ─ 署名つきの決まった操作 ─▶ 窓口 self-harden.php(お店に置く素の PHP 1 枚)
      │                                        │
      └ 公式の配布物・公開の弱点情報を調べる      └ 読む・試験場で試す・公式の中身を置く・戻す
```

- `api/` 頭。Claude(claude-opus-5-5)を呼び、次の一手を決め、お店の窓口を 1 歩ずつ呼びます。お店に Claude の API キーは置きません。
- `plugin/` プラグイン。お店に窓口を置き、API と鍵を交換し、管理画面に点検の経過と報告、健康診断を出します。
  - `SelfHarden/` EC-CUBE 4.0〜4.3(1 つのプラグインで全部の系列に入ります)
  - `SelfHarden3/` EC-CUBE 3.0
  - `SelfHarden2/` EC-CUBE 2 系の、PHP 7 以上で動いているお店(確かめたのは 2.17.2)
- `demo-servers/` 手元だけで動かす、古い版のデモ用のお店(2 系、3 系、4.0〜4.3、mod_php と PHP-FPM)。
- 窓口は、自分の居場所を見て、版の系統ごとの「地図」(書いてよい場所、版の読み方、公式の置き場)を自分で選びます。

つなぎ目は [docs/api.md](docs/api.md)、窓口の守り方は [docs/security.md](docs/security.md)、設計は [docs/design.md](docs/design.md)、決めたことの理由は [docs/decisions.md](docs/decisions.md) にあります。

## 守る線

守る道具が裏口になったら終わりなので、次の線を守っています。

- **鍵が漏れても、好きなプログラムは置けない。** 窓口ができるのは、決まった操作だけです。プログラムのファイルは、窓口が自分で取ってきた公式の中身(EC-CUBE と部品の公式の GitHub。配布物はチェックサムで確かめる)でしか置けません。どこから取るかは窓口が決め、API が渡せるのは「どの版か」だけです。`eval` や `include`、`exec` のたぐいは持っていません。
- **呼び出しは全部、署名つき。** HMAC-SHA256 の署名、時刻のずれは前後 300 秒まで、同じ呼び出しは 1 回きり。返事にも署名を付けます。
- **API を呼び放題にさせない。** 1 回の点検の費用の上限(初回 12 ドル、2 回目から 6 ドル)、お店ごとの 1 日の回数と費用の上限があります。
- **お店を壊さない。** 書く前に必ず控えを取り、書いたらすぐにお店を開いて確かめ、だめならその場で戻します。お店の改造(公式と違うファイル)は上書きしません。
- **API キーは各自のもの。** オープンソースとして使うときは、使う人が自分の Claude の API キーで API を動かします。

窓口のテストは `plugin/tests/run.sh` で、PHP 8.1 と 7.4 の両方で流します(4 系の地図 233 件、3 系 21 件、2 系 23 件)。

## Claude に送るもの、送らないもの

点検のあいだ、API は窓口から読んだものを Claude(Anthropic の API)に渡し、次の一手を決めさせます。

送るもの:

- PHP の版と動かし方、php.ini の設定(名前に password・secret・key を含むものは伏せる)、拡張、Web サーバーの名前とモジュール、置き場所のパス
- EC-CUBE の版、composer.lock の部品の一覧、.env の項目の名前(値は true・false などの決まった語のほかは伏せる)
- ファイルの一覧(名前・大きさ・日時・権限)と、公式の配布物との違いの一覧
- Agent が要ると判断したファイルの中身と、公式との差分(本体・部品のファイルと、.htaccess・.user.ini などの設定ファイル。1 ファイル 256KB まで)
- お店の画面を外から開いた結果(状態、ヘッダー、本文の頭の 4KB。Cookie は除く)
- 貼られたお知らせの URL と、公開の弱点情報

送らないもの:

- データベースの中身(お客さんの名前や住所、注文)。窓口はデータベースにつなぎません
- 秘密の設定ファイル(4 系の .env の値、3 系の config.yml・database.yml・mail.yml、2 系の data/config/config.php)。窓口が読むのを断ります
- 管理画面や FTP のパスワード。そもそも預かりません

点検の経過と結果は、API を動かしている場所(`api/data`)に残ります。API を自分で動かせば、記録も自分の手元だけに残ります。Claude に送ったデータの扱いは、Anthropic の API の規約によります。

## 動かし方(手元)

1. Claude の API キーを、リポジトリの直下の `.env` に書きます(`.env.example` を写して使ってください)。
2. Docker のネットワークを作り、API を立てます。

   ```sh
   docker network create self-harden
   cd api && docker compose up -d --build
   ```

3. デモ用のお店を立て、プラグインを入れて API とつなぎます。

   ```sh
   cd demo-servers
   docker compose --profile build-only build
   docker compose up -d server-b-php server-b
   ./install-plugin.sh server-b
   ./connect-plugin.sh server-b
   ```

4. お店の管理画面(http://127.0.0.1:8082/admin 、デモの初期値は admin / password)で、オーナーズストア → プラグイン → Shisa を開き、お知らせの URL を貼って「通知を渡す」を押します。経過がその場で流れます。

本物のお店に入れるときは、管理画面からプラグインのファイル(`plugin/build-zip.sh` などで作る zip や tar.gz)を上げて有効にし、「API とつなぐ」を押します。FTP のパスワードも、管理画面のパスワードも預かりません。

## まだできないこと

- **データベースの作り変えが要る版上げ**(たとえば 4.2.0 → 4.2.3)。プラグインの中で公式のマイグレーションを流す道はありますが、控えを取ること、失敗したら戻すこと、店主さんの許可(メンテナンスに入れてよいか)がそろってからにします。今は「店主の判断を待つ」として報告します。
- **3 系の部品の入れ替えを含む修正版**(3.0.18-p3 以降)。部品の読み込み表は composer が作るファイルで、公式の置き場がありません。窓口の中の決まった手順で組み立て、試験場で確かめてから置き換える形を考えています。
- **EC-CUBE 以外**。考える部分(調べる・試す・入れる・確かめる)はそのまま使えます。WordPress など、ほかの PHP のオープンソースにも、窓口の地図を足して広げていきます。
