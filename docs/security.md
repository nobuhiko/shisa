# 受け口の守り

守る道具が裏口になったら終わりなので、受け口(`self-harden.php`)は「鍵を持たない人には何もできない」「鍵を持っていても決まったことしかできない」の 2 段で作っています。テストは `plugin/tests/run.sh`(PHP 8.1 と 7.4 の両方で、4 系の地図 233 件、3 系の地図 21 件、2 系の地図 23 件)。窓口は自分の居場所のファイルの目印で版の系統の「地図」を選びます。API からは選べません。3 系と 2 系では、鍵と控えを公開の場所の外(`app/self-harden/`、`data/self-harden/`)に置き、設定ファイル(データベースのパスワードなど)は読ませません。

## 形

- 素の PHP 1 枚。EC-CUBE も Composer も読み込まない。ほかのファイルを `include` しない
- 操作は決まった種類だけ(`ping` `inspect` `list_dir` `read_file` `write_file` `restore` `list_backups` `lab_arm` `hash_tree` `restore_official` `quarantine` `release_quarantine` `list_quarantine` `audit_tail` `apply_official_fix` `apply_official_release` `clear_cache` `scan_custom`)。コードを渡して動かす操作は無い。`scan_custom`(カスタマイズの点検)は読むだけで、中身は窓口の手元で調べ、怪しい行(長い文字列は伏せる)だけを返す
- **本体の PHP のファイルを書くときは、中身を受け口が自分で決まった公式の場所から取ってくる**(`restore_official`)。API が渡せるのは「どのファイルを、公式のどの版にするか」だけで、中身も URL も渡せない。鍵が漏れても、書けるのは公式の中身だけ
- 鍵は `var/self-harden/config.php`。1 行目が PHP の `exit` なので、Web から開かれても中身は出ない。受け口は `include` せずに文字として読む
- `var/self-harden/` には `Require all denied` の `.htaccess` も置く

## 店主の承認で直す(3 本目)と考えた攻撃

カスタマイズしたコードの弱点は、制作会社を探して待つと間に合わない。そこで、Agent が直し方を提案し、店主が管理画面で中身を見て承認したものだけを窓口が書く。窓口が置けるプログラムは「公式の中身か、店主が承認したものだけ」になる。承認はお店の中に閉じ込める。

## 店主の承認で版上げする(4 本目、ブランチ feature/migration-approval)と考えた攻撃

データベースの作り変えが要る版上げ(4.2.0 → 4.2.3-p2 など)は、店主さんには手が出せず、Shisa も勝手にはしない。そこで、Agent が版上げを提案し、店主が管理画面で承認したときだけ、窓口が公式の手順(doc4.ec-cube.net/update42x)をメンテナンス中に行う。中身は公式の配布物だけで、窓口がチェックサムで確かめて取る。窓口(`self-harden.php`)は EC-CUBE を読み込まない決まりのままにし、データベースの作り変え(スキーマの差の反映と公式のマイグレーション)だけは、プラグインが置く別の入口(`self-harden-upgrade.php`)が、上げ先の公式の版の EC-CUBE を読み込んで行う。

| 攻撃 | 防ぎ方 | テスト(`plugin/tests/receiver_upgrade_test.php`) |
|---|---|---|
| API の鍵を盗んだ者が、承認なしで版を上げ下げする | 窓口の `upgrade` は、お店の中の承認の鍵で作った印(お店・提案・今の版・上げ先の版・期限)が無ければ始めない | 印なし / 偽造 / API の鍵で作った印 / 別のお店 |
| 承認と違う版に上げる・古い版に下げる | 印に今の版と上げ先の版を入れる。窓口は今の版が印と同じこと、上げ先が同じ系列の新しい公式のタグであることを確かめる。中身は窓口が公式の置き場から取り、公式のチェックサムで確かめる | 今の版が違う / 系列の違う版 / 同じか古い版 / 版の形 |
| 古い承認を使い回す | 期限 30 分、使った印は記録して 2 回目は断る。始めた作業は、始めたときの印でしか進められない | 使い回し / 作業と違う印 |
| データベースの入口を、外から好きに動かす | 入口は、窓口が「データベースの段」で置く 1 回きりの合図(64 けたの乱数、確かめる前に消す)と、作業の記録が「データベースの段」であることがそろったときだけ動く。行うのは決まった 2 つ(スキーマの差の反映と公式のマイグレーション)だけで、外から渡せるものは作業の名前と合図だけ。それ以外は 404 | 合図なし / 違う合図(合図は消える)/ 段が違う / 置き場が無い / 名前の形 |
| 版上げでカスタマイズを上書きする | 窓口が、今の版と上げ先の版の公式の配布物を両方取って見比べ、版のあいだで変わるファイルのうち、お店のものが今の版の公式と違うもの(カスタマイズ)が 1 つでもあれば、何も書かずに止める(メンテナンスにも入れない)。版のあいだで変わらないファイル(.htaccess など)は、お店のものをそのまま残す。カスタマイズの置き場・プラグイン・アップロード・`var/`・`.env` は触らない | (手元のデモのお店で確かめる) |
| データベースから消す・名前を変える変更を、勝手に流す | 入口は、まずスキーマの差を SQL で出し、テーブルや列を消す・名前を変える変更があれば何もしない(SQLite が列を足すときの作り直しは除く)| (手元のデモのお店で確かめる) |
| 途中で失敗して、お店が壊れたままになる | 先にファイルとデータベースの控えを取る(SQLite はファイルごと、MySQL はテーブルごとの作りと中身)。どの段で失敗しても、控えからファイルとデータベースを戻し、キャッシュを消し、お店を開いて確かめてからメンテナンスを外す。戻しても開けないときは、メンテナンスのまま止め、控えの場所と戻し方を店主に知らせる | (手元のデモのお店で、わざと失敗させて確かめる) |

## 残る危うさ

- **版上げのデータベースの段だけは、窓口の外で EC-CUBE を読み込む。** 読み込むのは、窓口がチェックサムで確かめた上げ先の公式の版で、決まった 2 つのコマンドだけを流す。入口は 1 回きりの合図がある間しか動かない。それでも、窓口の「EC-CUBE を読み込まない」という線の外にある部分なので、ここに書いておく
- **版上げの段は、1 回の呼び出しで長くかかるものがある**(配布物を取る・広げる・見比べる。手元では数十秒)。PHP の実行時間の上限が 30 秒で延ばせないサーバーでは、途中で止まるおそれがある。止まっても、お店にまだ書いていない段なら何も変わらず、書き始めたあとなら控えから戻す
- **途中で止まった版上げを、メンテナンス中のまま放っておかない。** 窓口は、10 分動きの無い作業を見つけたら、点検のたびの ping・inspect でも自分で着地させる(書き始めていれば控えから戻してメンテナンスを外す。書く前なら断って片付ける。戻しの途中なら戻しを続ける)。API は、動いている間だけ承認の印を控え、再起動しても続きから駆動し、窓口に届かなくても長めの間隔でもう一度試す。それでも自動で戻せないとき(戻したあとも開けない等)は、メンテナンスのまま黙って止めず、管理画面と点検の報告に、店主にわかる言葉で「今メンテナンス中のまま」「止まった作業を戻す」ボタン・メンテナンスの外し方を出す
- **調べたときからファイルが変わっていたら、版上げしない。** 提案に、版上げが触る場所(vendor/ の全部と置き換える本体のファイル)の指紋を記録して承認の印に入れ、窓口が始める前とメンテナンスに入る直前に取り直す。違えば何も書かずに止め(stale)、API はすぐに点検し直して提案し直す
- **点検で当てた部品の修正版のほうが新しい部品は、版上げで上書きしない**(新しいほうを残す。残す部品は承認の画面に出し、印に入れる)
- **店主が先にメンテナンスにしているお店は、版上げを断る**(成功したあとにメンテナンスを外すかで迷わないように。先に外してもらう)
- **データベースの入口は、窓口と同じ読み方で DATABASE_URL を解く**(%kernel.project_dir% はお店の root、sqlite:/// は root からの相対、sqlite://// は絶対)。窓口が控えを取ったデータベースと、つないだ先が違えば何もしない。お店のテーブルを一から作る SQL が出たら(つないだ先が違うおそれ)何もしない
- **控え(データベース・ファイル)は 0600 で、作業の置き場には外から開けない設定を置く。** 終わって 7 日たった控えは片付ける
- **版上げでは、部品(vendor/)を公式の手順どおり上げ先の版で上書きする**(点検で当てた修正版のほうが新しい部品は除く)。残した部品は、composer.lock と vendor/composer/installed.json では上げ先の配布物の版のまま見える(部品ごとの修正を当てたときと同じ扱い。Shisa は当てた記録で照らし合わせる)
- **版上げの間、管理画面の呼び出しが一時的に答えないことがある**(ファイルを置き換えている数秒)。画面は 10 秒で切って見に行き直す
- **MySQL の控えと戻しは、手元ではまだ試していない**(デモのお店は SQLite)。PostgreSQL は控えを取れないので、版上げはしない
- **MySQL の控えは JSON で取るので、バイナリの列(BLOB など)は形が変わることがある**(EC-CUBE の標準のテーブルには無い。プラグインが足したテーブルにあれば、戻したときに崩れるおそれ)

- **承認の鍵と API の鍵は、同じ場所(`var/self-harden/`、0700)にある。** お店にファイルを読める弱点があって両方が漏れると、好きな PHP を書ける。鍵は作った瞬間から自分だけが読めるように作る(`umask(0077)`)。これから、窓口が検証用の公開鍵だけを持ち、署名の秘密鍵はプラグイン(またはデータベース)に置く形(ed25519、`sodium`)にする
- **管理画面に別の XSS があれば、** 画面の中の JavaScript が、確認コードを読んで承認を送れてしまう。確認コードは「うっかり押す」を防ぐもので、管理画面そのものが乗っ取られたときの守りではない。パスワードの打ち直しを求める形は、これから
- **承認したコードは、そのままお店で動く。** `app/Customize` の PHP は毎回読み込まれ、テンプレートも信頼されたものとして動く。だから承認の画面に、固定の文でそう書き、危ない書き方には色を付ける。判断は店主に任せている

- 鍵を持つ者は、古い退避に `restore` で戻すことで、あとから足した守りの行を外すことができる(退避から戻す操作は、壊れたときの命綱なので止めていない)。記録(`audit.log`)には残る


- **鍵が漏れたら**、その店の `.htaccess` / `.user.ini` を書き換えたり、ファイルを隔離したりして店を止めることはできる(戻すための退避と隔離は残る)。本体を公式の別のコミットの中身にすることもできる(公式のブランチやタグから辿れるコミットだけ。版が今より古いものは断る)。自分の PHP のコードを動かすこと、決まった場所の外に書くこと、`.env` の値を読むことはできない
- **API が乗っ取られたら**、上と同じことができる。API の鍵の置き場は、手元では `api/data/`、公開するなら暗号化した保存先にする
- `.htaccess` の決まりは、全部の書き方を読み解くものではない。怪しい行は断る方に倒している。抜けが見つかったらテストに足して塞ぐ
- http の店では、通り道で中身を見られる。改ざんは署名で弾くが、中身(サーバーの設定の一覧)は見える。本番は TLS が前提
